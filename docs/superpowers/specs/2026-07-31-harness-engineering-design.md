# 하네스 엔지니어링 설계 문서

**날짜:** 2026-07-31  
**프로젝트:** 삼선 ERP (proim)  
**작성자:** AI + 프로젝트 기획자  

---

## 1. 개요

비개발자(바이브 코더) 2~3명이 AI와 협업해 ERP를 일관성 있게 개발·유지보수할 수 있도록 하는 하네스 엔지니어링 구조 정의.

**초기 규모:** 사용자 20~30명  
**목표:** SaaS 전환 가능한 확장 가능 구조  
**기술 스택:** Next.js + Supabase + Vercel  

---

## 2. 핵심 원칙

1. 모든 개발 주기는 문서화하고 CLAUDE.md에 링크로 연결
2. 비개발자가 스킬 3개만으로 전체 개발 주기를 수행 가능
3. 모든 기능의 기획·설계·개발·테스트 산출물을 Git 레포 내 보관
4. 처음부터 SaaS 전환을 대비한 멀티테넌트 구조 적용

---

## 3. 레포 구조

```
proim/
├── CLAUDE.md                        # 하네스 진입점 (링크 허브)
├── app/                             # Next.js ERP 앱
├── .claude/
│   └── skills/                      # new-feature, fix, status 스킬
├── features/                        # 모든 기능의 생애주기 문서
│   └── FEAT-NNN-기능명/
│       ├── 01-spec.md               # 아이디에이션 결과
│       ├── 02-design.html           # HTML 목업 SSOT
│       ├── 03-decisions.md          # 개발 결정사항
│       ├── tasks/
│       │   └── TASK-NNN-태스크명/
│       │       ├── spec.md          # 태스크 상세 정의
│       │       └── artifact.md      # 개발 진행/결과 요약
│       └── 06-test-cases.md         # E2E 수동 테스트 케이스
└── docs/
    └── harness/                     # 하네스 자체 문서
        ├── cycle.md                 # 8단계 개발주기 설명
        ├── new-feature.md           # new-feature 스킬 사용법
        ├── fix.md                   # fix 스킬 사용법
        └── status.md                # status 스킬 사용법
```

## 4. 8단계 개발 주기

| 단계 | 명칭 | 산출물 | 담당 |
|------|------|--------|------|
| 1 | 아이디에이션 | `01-spec.md` | AI + 기획자 |
| 2 | 디자인 | `02-design.html` | AI + 기획자 |
| 3 | 개발 결정사항 | `03-decisions.md` | AI + 기획자 |
| 4 | 태스크 분리 | `tasks/TASK-NNN/spec.md` | AI |
| 5 | 태스크별 개발 | `tasks/TASK-NNN/artifact.md` | AI |
| 6 | 테스트 케이스 생성 | `06-test-cases.md` | AI |
| 7 | 피드백 반영 | 해당 단계 문서 업데이트 | AI + 기획자 |
| 8 | 배포 | Vercel 프로덕션 반영 | AI (명령 실행) |

---

## 5. 스킬 명세

### 5.1 `/new-feature` — 풀 사이클 오케스트레이터

- **진입:** 사용자가 `/new-feature` 호출
- **FEAT 채번:** 기존 `features/` 폴더에서 최대 번호 + 1 자동 채번
- **브랜치 생성:** `feat/NNN-기능명` 자동 생성
- **흐름:** 1→2→3→4→5→6→7→8 순서, 각 단계 완료 시 사용자 확인 후 진행
- **단계 복귀:** 7단계에서 피드백 시 해당 단계로 돌아가 재진행 가능

### 5.2 `/fix` — 간소화 사이클

- **진입:** 사용자가 `/fix` 호출
- **FIX 채번:** `FIX-NNN-설명` 형태로 채번 (독립 폴더)
- **브랜치 생성:** `fix/NNN-설명` 자동 생성
- **흐름:** 문제정의 → (결정사항) → 태스크분리 → 개발 → 테스트 → 배포
- **디자인 단계 생략:** 디자인 변경이 필요한 경우에만 포함

### 5.3 `/status` — 현황 대시보드

- **진입:** 사용자가 `/status` 호출
- **동작:** `features/` 전체 스캔 → 각 폴더의 현재 단계 및 artifact.md 최종 수정일 읽기
- **출력:** 기능별 현재 단계, 마지막 업데이트 날짜 표 형태로 출력

```
┌─────────────────────┬──────────────┬──────────────────┐
│ 기능                │ 현재 단계     │ 마지막 업데이트   │
├─────────────────────┼──────────────┼──────────────────┤
│ FEAT-001 로그인     │ 5/8 개발중   │ 2026-07-30       │
│ FEAT-002 대시보드   │ 2/8 디자인   │ 2026-07-29       │
│ FIX-003 버튼오류    │ 완료         │ 2026-07-28       │
└─────────────────────┴──────────────┴──────────────────┘
```

---

## 6. 브랜치 전략

```
main          # 프로덕션 (Vercel 자동 배포)
  └── dev     # 통합 브랜치 (완료 기능 검증)
        ├── feat/001-로그인
        ├── feat/002-대시보드
        └── fix/003-버튼오류
```

**규칙:**
- 스킬 시작 시 AI가 브랜치 자동 생성
- 태스크 개발은 해당 `feat/*` or `fix/*` 브랜치 안에서만 진행
- 완료 후 `dev` 머지 → Vercel Preview URL로 확인
- 최종 승인 후 `main` 머지 → 프로덕션 자동 배포

---

## 7. 배포 파이프라인

```
로컬 개발 (Next.js dev server)
    ↓ 스킬 [8단계]
feat/* 또는 fix/* 브랜치 커밋
    ↓
dev 브랜치 머지 → Vercel Preview 자동 배포
    ↓ 팀 확인
main 브랜치 머지 → Vercel 프로덕션 자동 배포
    ↓
실사용자 접속 (20~30명)
```

---

## 8. SaaS 전환 대비

- **Supabase Row Level Security(RLS):** 초기부터 데이터 격리 적용
- **tenant_id 컬럼:** 모든 테이블에 필수 포함 (03-decisions.md 고정 규칙)
- **멀티테넌트 확장:** RLS + tenant_id 구조로 대규모 리팩토링 없이 SaaS 전환 가능
